# Pipeline audit: скользящая 5Y-норма и хранение истории

Аудит проведён 2026-06-07 по запросу. Режим: только чтение кода и листинг файлов, без сетевых запросов и без запуска скриптов сбора. Скрипты: `scripts/build_fy_norm.py`, `scripts/compute_sector_scores.py`, `scripts/update_all.py`, `scripts/backfill_history.py`. Данные: `data/market_quotes/`.

---

## 1. Пересчёт 5Y-нормы во времени: норма СТАТИЧНА (захардкожена FY2021–FY2025)

**Ответ: НЕТ, норма не скользит и не пересчитывается автоматически по дате. Окно лет фиксировано константой в коде.**

Доказательства из кода:

- `scripts/build_fy_norm.py:109` — `FY_YEARS = [2021, 2022, 2023, 2024, 2025]` — годы заданы литералом на уровне модуля, не вычисляются.
- `scripts/build_fy_norm.py:1659-1660` — аргумент `--years` имеет `default=None`. Если его не передать, годы остаются дефолтными.
- `scripts/build_fy_norm.py:1724-1725` — `if args.years: FY_YEARS = args.years`. Override происходит ТОЛЬКО при явной ручной передаче `--years`. Авто-вычисления нет.
- `scripts/build_fy_norm.py:1052` и `:1377` — построение норм-строк идёт прямым циклом `for year in FY_YEARS:` по этой же константе.
- `scripts/build_fy_norm.py:1753` — `as_of = args.as_of or dt.date.today()`. Это ЕДИНСТВЕННОЕ место, где скрипт берёт сегодняшнюю дату, и оно относится к режиму `--current` (снимок), а НЕ к выбору лет нормы. Норм-ветка (`else` на `:1818`) сегодняшнюю дату не использует вообще.
- Поиск по всему файлу: `date.today()` встречается один раз (строка 1753, только для `--current`); `datetime.now()` — дважды (строки 1552, 1627), только как `generated_at` в метаданных. Логики «прошёл месяц / появился новый фискальный год → дотянуть и пересчитать норму» нет ни в одном скрипте.

Вывод по (а)(б)(в)(г) из вопроса:
- (а) скрипт определяет сегодняшнюю дату только для current-снимка, не для нормы;
- (б) понимание «прошёл месяц / новый FY» — ОТСУТСТВУЕТ;
- (в) автодотягивание недостающих годов нормы — ОТСУТСТВУЕТ;
- (г) автопересчёт 5Y-нормы — ОТСУТСТВУЕТ.

Чтобы получить, например, окно FY2022–FY2026, придётся вручную запустить `build_fy_norm.py ... --years 2022 2023 2024 2025 2026` по каждому сектору. `update_all.py` этого НЕ делает (см. раздел 2).

**Рекомендация (доделать):** ввести скользящее окно. Вариант: новая функция вроде `default_fy_years(as_of, window=5)`, которая по `as_of` возвращает последние 5 завершённых фискальных лет (с учётом лага подачи 10-K ≈ 60–120 дней, чтобы не включать год, отчёт по которому ещё не подан). Подключить её как default вместо литерала `FY_YEARS` на `:109`. Плюс отдельный ежемесячный скрипт-обёртка (см. раздел 2), который решает, нужно ли вообще двигать окно, и пересобирает норму только когда в SEC появился новый годовой отчёт.

## 2. Переиспользование свежих данных: ЧАСТИЧНО (SEC-кэш общий, но норму update_all не трогает)

**Ответ: ЧАСТИЧНО. SEC-факты переиспользуются обоими режимами через общий дисковый кэш (`.sec_cache`), но регулярный `update_all.py` обновляет только current+score и НИКОГДА не пересчитывает норму. Связи «накопили current-снимки → пересобрали норму» нет.**

Доказательства из кода:

- Общий SEC-кэш для обоих режимов: и норм-ветка (`fetch_series`, `scripts/build_fy_norm.py:423-456`), и current-ветка (`fetch_series_asof`, `:479-510`) вызывают одну и ту же `fetch_concept_units` (`:305-329`), которая сначала читает кэш `read_sec_concept_cache` (`:308-311`) и пишет его `write_sec_concept_cache` (`:327-328`). То есть при пересчёте нормы SEC-факты тоже берутся из кэша, не только для current. На диске кэш реально большой: `.sec_cache/` содержит ~3150 файлов.
- НО кэш имеет TTL 7 дней: `SEC_CACHE_MAX_AGE = dt.timedelta(days=7)` (`:84`), проверка `if age >= SEC_CACHE_MAX_AGE...: return False` (`:273-275`). После 7 дней запись считается протухшей и факт качается из сети заново. Цены (Twelve Data / FMP / Nasdaq) НЕ кэшируются на диск вообще — каждый запуск тянет их заново.
- `update_all.py` обновляет только current+score, а не норму. Прямо в докстринге: `scripts/update_all.py:12-15` — «The 5Y NORM itself ... is NOT refetched here — it is a once-a-year job». Код подтверждает: единственная сборочная команда — `run_current` (`:111-115`), которая всегда вызывает `build_fy_norm.py ... --current`; затем `run_score` (`:118-125`). Вызова `build_fy_norm.py` без `--current` (т.е. пересборки нормы) в `update_all.py` нет.
- Связь между current-снимками и нормой — отсутствует. Норма (`fyn_<slug>_norm_summary.csv`) собирается отдельным ручным прогоном; накопленные current-снимки (10/20/30) в неё не вливаются. `compute_sector_scores.py` лишь делит current на норму (`load_real_norms` `:190-209` читает `fyn_<slug>_norm_summary.csv`; `load_real_current_summaries` `:255+` читает `fyn_<slug>_current_summary.csv`), но саму норму не обновляет.

Итого: при ручном пересчёте нормы свежие SEC-факты переиспользуются (если им < 7 дней), но автоматического переиспользования накопленных current-снимков для обновления нормы нет, и `update_all` норму не двигает.

**Рекомендация (доделать):** добавить в `update_all.py` режим/шаг `--refresh-norm` (или отдельный `scripts/refresh_norm.py`), который раз в месяц проверяет, не появился ли в SEC новый годовой факт, и при необходимости запускает `build_fy_norm.py` (без `--current`) со скользящим окном из раздела 1 по всем секторам. SEC-кэш это удешевит (повторные факты не качаются, пока им < 7 дней). Опционально — увеличить `SEC_CACHE_MAX_AGE` для годовых фактов (они почти не меняются после подачи), чтобы пересчёт нормы был полностью офлайновым между сезонами отчётности.

## 3. Хранение истории: ЧАСТИЧНО (датированные current сохраняются; undated current и норма перезатираются; единого архива нет)

**Ответ: ЧАСТИЧНО. Датированные current-снимки (`--as-of`) НЕ перезатираются и копят историю. Но недатированный «сегодняшний» current и норма перезаписываются при каждом запуске; норма вообще нигде не версионируется; цены сырыми не сохраняются. Единого архива всех точек нет — данные разбросаны по сотням файлов.**

Доказательства из кода и файловой системы:

(а) Датированные current-снимки НЕ перезатираются — история копится:
- `scripts/build_fy_norm.py:1733-1739` — при `--current --as-of` суффикс имени = `current_{YYYYMMDD}`, поэтому каждая дата пишется в свой файл `fyn_<slug>_current_<YYYYMMDD>(_summary).csv/.json`.
- `scripts/backfill_history.py:152-162` (`dated_stem`/`dated_paths`) формирует те же датированные имена; снимки с готовым P/E пропускаются (`snapshot_quality` `:184-203`), backfill безопасно возобновляем — старое не трётся.
- На диске реально лежат серии по 10 датированных снимков на сектор (например `fyn_agriculture_chemicals_current_20250910 ... _20260510`). Это сохранённая история. ОК.

(б) Недатированный current ПЕРЕЗАТИРАЕТСЯ при каждом `update_all`:
- `scripts/build_fy_norm.py:1736-1739` — без `--as-of` суффикс = просто `current`, путь фиксированный: `fyn_<slug>_current.csv`, `_current_summary.csv`, `.json`.
- `update_all.run_current` (`scripts/update_all.py:111-115`) вызывает `--current` БЕЗ `--as-of`, значит каждый прогон перезаписывает один и тот же `fyn_<slug>_current_summary.csv`. На диске их ровно по 17 (по одному на сектор), даты модификации меняются. Вчерашний недатированный снимок теряется. Частично спасает то, что десятидневный backfill всё же кладёт датированную копию — но обычный `update_all` (без `--as-of`) датированную копию НЕ создаёт, так что промежуточные ежедневные точки между якорями 10/20/30 не сохраняются.

(в) SEC-кэш хранит сырые факты, но с TTL 7 дней (не «надолго»):
- `scripts/build_fy_norm.py:84` `SEC_CACHE_MAX_AGE = 7 days`; `:273-275` протухшие записи игнорируются и перекачиваются. Кэш — это ускоритель, а не архив; на горизонте месяцев он не сохраняет историю фактов. 404-ответы кэшируются как `{"_sec_cache_status":404}` (`:319-324`).

(г) Норма перезатирается и нигде не датируется:
- Норм-выход пишется в фиксированные `fyn_<slug>_norm(.csv/_summary.csv/.json)` (`scripts/build_fy_norm.py:1737-1739`, суффикс `norm`). Датированных норм-файлов на диске нет (`ls fyn_*_norm_????????*.csv` → пусто). Значит при будущем пересчёте старая 5Y-норма будет затёрта без следа — нельзя будет воспроизвести, какой норме соответствовал прошлый score.

(д) Единого архива нет — данные разбросаны:
- История = сотни файлов вида `fyn_<slug>_current_<date>_*` в плоской `data/market_quotes/`; агрегаты — `sector_scores.csv/.json`, `sector_scores_preview*.csv`, `sector_scores_preview_monthly.csv`. Нет единой таблицы «дата × сектор × метрика × значение × источник» как долговременного хранилища. `sector_scores*` перезаписываются (`compute_sector_scores.write_csv` `:500-506`, `write_json` `:700+` пишут в фиксированные пути).

**Оценка потери данных:** датированные точки valuation сохраняются и не теряются (главная история цела). Теряются: (1) промежуточные недатированные current-снимки между якорями; (2) предыдущие версии 5Y-нормы при пересчёте; (3) сырые цены (нигде не кэшируются); (4) старые сырые SEC-факты по истечении 7-дневного TTL.

**Рекомендация (доделать):**
1. Версионировать норму: при пересборке писать также `fyn_<slug>_norm_<YYYYMMDD>_summary.csv` (как уже сделано для current), чтобы каждый score можно было привязать к конкретной версии нормы.
2. Завести единый append-only архив всех точек (например `data/market_quotes/history/points.csv` или SQLite) со схемой `as_of, sector, metric, current_value, norm_value, coefficient, source, status`, куда `compute_sector_scores`/`update_all` дописывают строки, не перезатирая. Это и есть «единое место, где ничего не пригождающееся не теряется».
3. Заставить `update_all` всегда писать датированную копию current (передавать `--as-of <today>`), чтобы ежедневные снимки тоже сохранялись, а не только якорные 10/20/30.

## Топ-3 приоритета для самоподдерживающейся скользящей 5Y-нормы

1. **Скользящее окно лет.** Заменить литерал `FY_YEARS` (`build_fy_norm.py:109`) на функцию от `as_of` (последние 5 поданных в SEC годовых отчётов), чтобы окно само сдвигалось.
2. **Ежемесячный авто-пересчёт нормы.** Добавить шаг/скрипт (`update_all --refresh-norm` или `scripts/refresh_norm.py`), который по дате решает, появился ли новый годовой отчёт, и пересобирает норму со скользящим окном, переиспользуя `.sec_cache`. Сейчас `update_all` норму вообще не трогает.
3. **Версионирование нормы + единый append-only архив истории.** Датировать норм-файлы и завести одну долговременную таблицу всех точек (date × sector × metric × value × source), чтобы ничего не перезатиралось.
